## 0. Top operator ask: the production deploy is NOT gated on merging to main — confirmed, and it just caused a live regression

**This supersedes an earlier, wrong theory drafted earlier in this same run.**
Original read: the live site was serving a signup-form fix that only existed
in an unmerged draft PR (#15), and I guessed someone had manually patched
production out-of-band. That guess is wrong. Here is what actually happened,
confirmed with direct evidence from this run:

1. Early in this run, before I'd pushed anything, the live site served
   `embed-subscribe/morty-morguelabs` (PR #15's fix), even though `main` has
   never contained that string (`git log --all` on every HTML file: zero
   hits) and PR #15 was never merged.
2. This run's own branch (`ops/weekly-2026-08-17`) touches only this report
   file — no HTML, no signup markup — and was built from `main`, which still
   has the old, dead slug (`embed-subscribe/morguelabs`).
3. I pushed that branch to open this PR. Cloudflare's own bot then commented
   on this PR: **"Deploying with Cloudflare Workers... Deployment
   successful... morguelabs... production"**, referencing this run's commit.
   Not "preview" — the comment says production.
4. I re-fetched the live site immediately after: it now serves
   `embed-subscribe/morguelabs` again — **the dead slug is back live, right
   now**, and subscriber capture is broken again as a direct, mechanical
   side effect of me opening a routine, content-free ops PR.

**Confirmed mechanism: pushing *any* branch to this repo deploys straight to
the production custom domain (morguelabs.com), independent of whether a PR
exists, is reviewed, or is merged.** It is not Cloudflare Pages gated on the
`main` branch, as this agent's standing brief describes — the bot identifies
itself as Cloudflare Workers, and behaves like a Git integration with no
production-branch restriction configured. Whichever branch was pushed most
recently wins the custom domain. That fully explains the original mystery
(PR #15's branch push on 2026-08-13 made its fix live, unreviewed) and this
run just reproduced the same bug in the opposite direction, undoing that fix.

**This is a direct, current break of the standing hard rule "the human
operator's merge IS the publication approval."** That rule is not currently
being enforced by the infrastructure. Every branch push, from any PR,
including future autopsy drafts, goes live immediately, before review.

**Immediate, live consequence right now:** the signup form on
morguelabs.com is broken (dead Buttondown slug), same failure mode as
before PR #15's investigation, and will stay broken until another push
happens to change what's live — most likely by re-pushing PR #15's branch
or merging it. I have not attempted either: fixing the signup URL is PR
#15's scope, not this run's, merging is reserved for the operator, and
pushing further branches only feeds the same unreviewed-deploy problem
rather than fixing it. The fastest safe remedy available to the operator is
merging PR #15 (or re-pushing its branch) to restore working subscriber
capture, and separately, fixing the Cloudflare Workers project's
build/deploy configuration (production-branch restriction /
preview-vs-production separation) so pushes stop landing on the live
domain unreviewed.

One consequence for §1 below: my health check for the literal string
`embed-subscribe/morguelabs` currently **passes** again, because the broken
slug is (again) what's live. That's a bad sign here, not a good one — see
above.
